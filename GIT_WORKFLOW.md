# Git & GitHub Workflow

Your project already has a git history (run `git log --oneline` to see it) —
this is what "good commit hygiene" looks like: each commit is one logical
unit of work with a message that explains *what* and *why*, not just "fix stuff".

## Pushing to GitHub for the first time

1. Create a new **empty** repository on GitHub (don't initialize with a
   README — you already have one, and it'll conflict)
2. Connect your local repo and push:
```bash
git remote add origin https://github.com/<your-username>/mediai-pro.git
git branch -M main
git push -u origin main
```

## Branching strategy for a solo/small-team academic project

You don't need a heavyweight workflow (that's for large teams), but even
solo, branches make your work easier to review and roll back:

- `main` — always deployable/working. Don't commit directly here for anything
  non-trivial.
- `develop` (optional) — integration branch if you want main to always be
  demo-ready while develop absorbs work-in-progress
- Feature branches — one per feature, e.g. `feat/appointment-booking`,
  `feat/ai-symptom-checker`, `fix/login-validation-bug`

Typical flow for adding a feature:
```bash
git checkout -b feat/notifications
# ... make changes ...
git add .
git commit -m "feat: add in-app notification bell"
git push -u origin feat/notifications
# Open a Pull Request on GitHub into main, review your own diff, merge
```

Reviewing your own PR diff before merging is a genuinely useful habit — you
catch bugs (console.logs left in, commented-out code, etc.) far more easily
in GitHub's diff view than scrolling through your editor.

## Commit message convention (what we used throughout this build)

```
<type>: <short summary>

feat:     a new feature
fix:      a bug fix
chore:    tooling, config, dependencies — no production code change
test:     adding or fixing tests
docs:     documentation only
refactor: code change that neither fixes a bug nor adds a feature
ci:       CI/CD pipeline changes
```
Examples from this project's actual history:
- `feat(server): MongoDB connection + JWT auth with RBAC`
- `feat: medical records with file upload (Multer)`
- `test: add backend (Jest+Supertest) and frontend (Vitest+RTL) test suites`

## What NOT to commit (already handled by .gitignore, but know why)

- `node_modules/` — regenerated from `package.json` via `npm install`;
  committing it bloats the repo massively and causes merge conflicts
- `.env` — contains secrets (JWT secrets, DB passwords, API keys). Only
  `.env.example` (with placeholder values) should ever be committed
- `dist/` / build output — regenerated by `npm run build`, shouldn't be
  source-controlled
- `uploads/*` (except `.gitkeep`) — user-uploaded files don't belong in git

## For your module submission / viva

- Make sure your final `git log` tells a coherent story — a marker skimming
  your commit history should be able to see the project taking shape step by
  step, matching your project report's timeline
- If you squashed/force-pushed and lost history, that's fine — just be able
  to explain your actual development process when asked
- The `.github/workflows/ci.yml` file (already set up) means every push
  triggers automated tests on GitHub's servers — you can show this running
  green in the "Actions" tab of your repo as evidence of testing discipline
